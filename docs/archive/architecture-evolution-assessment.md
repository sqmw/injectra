性质：源码与工程结构评估、候选演进建议；不替代[现行架构](../architecture/boundaries.md)或[D-003产品边界](../DECISIONS.md#d-003)，不代表已批准重构。当前交付仍为runtime Web注入；原生/内存操作只用于检验长期扩展空间。

## 结论

保留Cargo workspace、共享Web单一来源、适配器依赖契约和CLI组合入口。无需重建仓库，也无需把架构图的六个分支机械变成六个crate。

当前结构是合格的Web/CDP MVP基础，但不是已经完成的通用注入架构。增加同类CDP宿主时复用条件较好；第二个Web接入实现需要核验执行语义；原生/内存操作需要新增执行域，不能直接塞入现有Session。

建议将下一次扩展与小范围边界整理一起推进：先明确Web契约归属及目标/结果语义，再随第二后端、第二平台或SDK的实际需求提取对应模块。当前没有仅因目录规模而必须立即实施的大重构。

## 已核对结构

Cargo metadata（offline、no-deps）确认5个crate，项目内依赖如下：

```text
cli -> core / payload / cdp / platform-macos
payload / cdp / platform-macos -> core
core -> 无项目内crate
payload -> 编译时嵌入唯一的web/runtime.js
```

目标源码共684行（含Rust内联测试）：core 63、CLI main 50、platform-macos 54；没有因文件膨胀而必须立即拆分的证据。行数仅用于判断整理规模，职责与契约才决定边界。

| 长期目标 | 现有基础 | 尚缺的证明或边界 |
| --- | --- | --- |
| 更多Chromium/CDP宿主 | cdp不识别应用名称，Web程序独立 | 实际入口、页面类型、端点路径和协议行为须逐场景验证 |
| Windows / Linux | CDP源码没有操作系统专属分支 | 构建/运行入口及目标OS实测；macOS启动规划不是通用启动器 |
| WebKit等其他Web运行时 | Engine/Session可替换，共享载荷不依赖CDP | 页面上下文、Promise等待、结果序列化、异常语义及DOM执行证据 |
| 原生接入后再进入WebView | 共享Web载荷可以保持 | 独立原生后端及WebView执行桥接；仅进程脚本成功不够 |
| 原生脚本、模块或内存操作 | Cargo模块化及依赖倒置可沿用 | 目标、载荷、能力和结果的专门契约；现有Web Session不能直接覆盖 |
| SDK或第二调用入口 | 4个库crate已可被调用 | 可复用的Web注入用例仍位于CLI，尚无稳定应用API |

## 扩展障碍与处理时机

### A-01 · core中的“通用”类型实际属于Web执行域

证据：[core/src/lib.rs](../../crates/core/src/lib.rs)的Target（第9行）强制title/url；Capability（第16行）只有EvaluateJavaScript；Session（第20行）接受源码字符串、返回JSON值。[web/runtime.js](../../web/runtime.js)第29行要求document.head/body，说明载荷需要页面DOM，并非任意JS环境。

影响：若强行沿用这些类型，原生进程会被迫伪造URL，或把原生操作编码为无类型字符串；仅“能执行JS”的后端也未必能够执行当前Web载荷。这是未来扩展的契约障碍，不据此否定当前page目标限定的MVP。

建议：在引入第二Web后端时明确Web目标/页面执行契约；在首次原生执行域进入前，把页面专属类型归入Web模块，公共core只保留实际共享的身份、错误和结果基础。不需要提前列举全部未来原生方法。

预期：Web后端可按同一语义验收，原生模块不污染Web接口。成本：迁移类型引用与测试；如外部JSON字段变化，需要兼容或版本化，不能借重构静默改变现有CLI输出。

### A-02 · CLI同时承担了最小用例流程与具体后端装配

证据：[cli/main.rs](../../crates/cli/src/main.rs)第17行加载/生成Web程序，第29–33行固定构造CdpEngine并连接执行；[cli/args.rs](../../crates/cli/src/args.rs)的targets/apply/remove均必须提供port。

影响：第二后端的接入信息可能不是端口，SDK直接复用现有用例也缺少公共入口。当前main仅50行，固定装配对单后端是合理实现，不属于应立即删除的业务堆积。

建议：第二后端或SDK被确定后，将“载荷准备→连接→执行”的可复用用例放入库模块，CLI继续负责参数解析和具体装配。用带后端归属的目标/连接配置表达输入；仅当出现聚合目标列表时，才需要跨后端命名空间，当前端口+ID已限定单个发现源。

预期：新增入口不复制流程；后端选择不扩散到共享载荷。成本：引入一个窄用例模块和装配测试；初期可在现有库内组织，不必立即新建application crate或插件注册中心。

### A-03 · 操作系统能力与宿主特征混在同一实现

证据：[platform-macos/src/lib.rs](../../crates/platform-macos/src/lib.rs)第20–44行同时处理.app路径/plutil和Electron Framework识别，第48行生成Chromium调试参数。

影响：第二类macOS宿主或第二OS出现时，按组合复制完整启动规划会重复系统路径和宿主规则。

建议：在下一项宿主接入规划或跨平台开发启动时，拆开系统应用包解析与宿主识别/参数规划；可以先拆内部模块，真实复用出现后再抽crate。保留当前只读启动规划和明确拒绝不支持宿主的行为。

预期：系统能力与宿主描述可分别复用。成本：现有规划逻辑和测试迁移；不能把非标准宿主的支持当作机械重命名附带交付。

### A-04 · 结果未知没有成为稳定的机器可判定合同

证据：[core/src/lib.rs](../../crates/core/src/lib.rs)第5行采用Box<dyn Error>；[cdp/session.rs](../../crates/cdp/src/session.rs)第47–99行将连接、协议、脚本等错误交给同一Result通道；[cli/main.rs](../../crates/cli/src/main.rs)第45–47行统一输出stderr并退出1。结果未知语义主要由文档说明，现有错误接口没有稳定分类。

影响：第二后端或SDK需要区分“执行前拒绝”“目标脚本异常”“发送后失联、结果未知”时，容易依赖错误字符串或各自解释。返回非零不等于页面没有产生副作用。

建议：在第二后端/SDK共用错误处理前，引入有阶段及执行确定性的错误/结果类型，并保留底层原因；维持不自动重放副作用操作。该调整不增加回滚或恢复平台。

预期：跨后端结果语义一致，调用者无需解析文字猜测执行状态。成本：梳理错误映射与故障测试；超时前是否已发送必须以实际执行边界为依据，不能把所有超时都标成同一种状态。

### A-05 · 验证结构尚未证明跨平台或跨引擎可替换

证据：[electron-smoke.mjs](../../scripts/electron-smoke.mjs)第10行明确拒绝非darwin，第90–92行耦合macOS启动规划；[test-env.mjs](../../scripts/test-env.mjs)第10行拼接固定debug二进制名，Windows路径解析未核实；[cargo.sh](../../scripts/cargo.sh)依赖POSIX shell。当前没有被Git跟踪的.github工作流。Web测试使用jsdom，真实注入证据见[验证记录](../validation.md)。

影响：现有测试能说明当前实现，但不能验证新增后端遵循同一页面执行语义；新增OS也缺少就绪的真实宿主验收入口。没有CI本身不是当前MVP缺陷。

建议：第二Web后端落地时提取共同的执行合同用例，并用各后端的真实fixture运行；跨平台开始时拆分通用注入断言与平台启动准备，提供明确可用的构建/测试入口。Windows命令及二进制解析需要在目标环境确认，不能仅凭文件名推定成功或失败。

预期：不同后端对目标、异常、Promise和返回值有一致证据。成本：第二真实环境及平台验证资源；只增加一个总返回成功的假后端不能关闭该缺口。

## 候选目录演进

以下为职责示意，不是本次要创建的目录清单，也不强制每个模块独立成crate：

```text
crates/
  cli/                  参数解析、装配、输出
  core/                 经真实用例确认的共有身份、错误、结果
  web/                  页面执行契约、Web载荷及用例
  cdp/                  CDP适配，沿用现有实现
  platform-macos/       macOS系统能力
  hosts/                宿主接入描述，出现复用后提取
  native/               未来原生执行域，真实需求到来再建
  backend-frida/        未来候选原生后端，未验证
web/                    现有共享JS保持单一来源
scripts/                构建/验收入口，平台差异进入小模块
tests/                  共同契约用例 + 各真实后端fixture
```

当前payload到候选web模块的职责映射是Web Bundle加载/生成；当前core中的页面Target/Session也属于候选Web域。共享JS可以继续保持现位置，调整归属不要求复制或为目录美观搬文件。现有Engine实际承担接入后端契约，若实施时改名，需要明确术语映射与兼容范围。

不建议现在引入动态插件ABI、全局后端注册中心、完整异步调度器或空的原生实现。它们均为非当前阻塞项：分别在独立插件分发、多后端动态发现、明确并发/持续消息需求、真实原生场景出现时再评估；当前同步单次执行并不能据此判为错误。

## 调整顺序与验收

| 触发条件 | 本阶段必要调整 | 可核对的验收 |
| --- | --- | --- |
| 仍只维护当前CDP Web MVP | 保留现结构；修正职责认识，不做目录大搬迁 | 现有命令及Web单一来源不漂移 |
| 下一项真实Web后端或SDK被确定 | A-01的Web语义、A-02用例边界、A-04结果类型、A-05共同合同 | 同一Bundle和同一合同用例经不同后端；不支持请求在执行前拒绝；发送后失联保留结果未知 |
| 下一平台或宿主规划被确定 | A-03与A-05的平台部分 | 当前macOS证据保留；新平台原生环境构建、注入及错误反馈有独立记录 |
| 首个原生/内存操作场景被确定 | A-01分域 + 专门原生目标/载荷/能力，按需桥接Web | 原生目标无需URL；CDP无空内存方法；进程脚本与页面执行分别验收 |

每次迁移只调整一个可验证边界，保留现有CLI、manifest v1和已实现辅助接口；行为或格式变更需明确版本迁移。源码改动按独立提交回退，历史实测证据不覆盖。迁移收益是限制新增后端的改动范围，尚未测量开发工时或跨引擎复用率。
